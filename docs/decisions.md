# 技术取舍清单

> 这份文件回答的是面试里最难的一类问题：**"你为什么不用 X？"**
> 每条都写清楚：当时的约束、选了什么、放弃了什么、代价是什么、有没有证据。

---

## A. 网关

### A1. 网关用 Go 标准库，而不是 FastAPI / nginx / Envoy

**约束**：一个人 1-2 天完成；要展示对并发、流式、超时的理解；不能变成"调框架"。

**选择**：Go + `net/http` + `prometheus/client_golang`，约 900 行，无 Web 框架。

**放弃的方案**：
- **Python FastAPI**：写起来最快，但 GIL 下每个流式连接仍要一个线程/协程，
  且"网关"这个位置的价值（低延迟、低内存、单二进制部署）体现不出来；面试官会问
  "你为什么用 Python 做流量入口"。
- **nginx / Envoy**：成熟，但 SSE 透传、按后端健康状态路由、按首字节超时重试这些行为
  需要写 Lua/WASM，调试成本比直接写 Go 高，且无法展示"我理解这些机制"。
- **httputil.ReverseProxy**：默认会缓冲响应、且不提供"首字节前重试"的钩子。

**代价**：要自己处理 hop-by-hop header、Flusher 断言、body 一次性、超时分层。
这些恰好是本项目最有价值的部分。

**证据**：`gateway/*.go`；`proxy_test.go` 用真实 `httptest` 服务验证流式与时序。

---

### A2. 默认 `least_conn`，同时保留 `round_robin`

**约束**：LLM 请求的生成长度差异可达一个数量级（8 token vs 512 token）。

**选择**：默认 `least_conn`（按 `running/weight`），`round_robin` 用 nginx 式**平滑加权轮询**
（权重 2:1 时顺序是 A,A,B 而不是 A,A,B,A,A,B，避免突发打满高权重实例）。

**为什么不用纯轮询**：轮询假设"每个请求代价相同"。LLM 场景下这个假设不成立：
一个长生成会把某实例的在途数拉到很高，而轮询还会继续往上叠。

**代价**：最少连接需要维护在途计数，且"选最小"与"计数 +1"之间存在竞态（见 A3）。

**证据**：`balancer.go`；`TestWeightedRoundRobinHonoursWeights`、`TestSmoothWeightedRoundRobinAvoidsBursts`。

---

### A3. "选择 + 计数"放在同一把短锁里，而不是 CAS 重试

**约束**：两个 goroutine 可能同时读到同一个最小 `Running`，都选同一台，再各自 `Add(1)`。
高并发下这会退化成"全部打一台"。

**选择**：`Pool.selMu` 保护"挑一个 + `Running.Add(1)`"整个临界区。
临界区只有几次 atomic load 和一次加法。

**放弃的方案**：
- **CAS 重试**：需要为每台后端维护版本号，失败重试的循环在高竞争下反而更难推理。
- **先 `Add(1)` 再检查**：会让 Running 短暂虚高，影响其他请求的判断。
- **每台后端一把锁**：仍然无法原子地比较两台。

**代价**：选择路径串行化。但 LLM 请求生命周期是秒级，网关的选择频率是几百 QPS 量级，
这把锁的争用可以忽略；用 `go test -race` + 200 goroutine 并发测试验证了正确性。

**证据**：`TestAcquireConcurrentDistributionAndRelease`（每个后端至少拿到 25%）。
CI 用 `-race` 跑。

---

### A4. 平局必须显式打破（真实踩坑）

**背景**：`least_conn` 用严格小于比较时，两个空闲实例 `Running` 都是 0，
比较永远为 false，`best` 永远是候选列表里的第一个。

**现象**：端到端压测（2 个 mock 后端、并发 1/4/8、共 124 请求）出现 **83 : 41** 的偏斜。
并发 1 的那一档 100% 打在第一台——因为每个请求开始时两台都是空闲的。

**选择**：`Running` 相同时比较 `TotalRequests`，再相同则按名字排序。

**代价**：`TotalRequests` 会长期略微偏向"用得少"的实例，但会自校正；
语义上从"纯最少连接"变成"最少连接 + 最少累计负载"。

**证据**：`TestLeastConnBreaksTiesRoundRobin`（20 次顺序请求必须 10:10）；
修复后同一端到端场景变成 **62 : 62**。这条写进 decisions 比写十行代码更能说明问题。

---

### A5. 健康检查主动探测，而不是只靠请求失败被动摘除

**选择**：每个后端独立 goroutine + `time.Ticker`，每 10s 探一次 `/health`。

**为什么不只用被动失败计数**：没有流量时，挂掉的实例永远不会被发现；
恢复的实例也永远不会被重新加入。主动探测能覆盖"空闲实例"。

**为什么用 `Ticker` 而不是 `time.Sleep` 循环**：Sleep 版本无法响应退出信号，
关闭时要等一个完整周期；`Ticker` + `select { case <-done }` 可以立即退出。
必须 `defer ticker.Stop()`——`time.Tick` 的 ticker 无法停止，会永久泄漏。

**连续 N 次才摘除 / 连续 M 次才恢复**：避免一次网络抖动就把实例摘掉，
也避免半启动的实例被过早加入。默认都是 2。

**代价**：最坏情况下故障发现延迟 ≈ `interval × unhealthy_after` = 20s。
对 LLM 服务可接受（请求本身就长）；需要更快可以调小间隔。

**证据**：`backend.go`、`TestHealthCheckRemovesAndRestoresBackend`、
`TestHealthCheckRequiresConsecutiveFailures`。

---

### A6. 探针不复用连接

**背景**：端到端测试里，mock 后端 `shutdown()` 后关闭了监听 socket，
但网关仍然报告它 healthy。

**原因**：探针 client 用了 keep-alive，复用了之前建立的 TCP 连接；
旧连接上的 worker 线程仍在服务请求，所以探针一直成功。
真实世界里对应"进程还在、但已经不再 accept 新连接"的亚健康状态。

**选择**：探针 transport 设 `DisableKeepAlives: true`。

**代价**：每 10s 多一次 TCP 握手，可忽略；换来的是探针语义正确：
**验证新请求能否成功，而不是验证旧连接是否还活着**。

**证据**：修复后同一场景 2 次探测内正确摘除（`probe_failures=2`）。

---

### A7. 软摘除，不打断在途请求

**选择**：健康状态只影响 `Acquire` 的选择；已经拿到后端引用的请求继续跑完。

**为什么**：一个 128 token 的生成可能正在 decode 到一半，硬杀会浪费已经消耗的 GPU 时间，
客户端还要重试。摘除的目的是"不再接新活"，不是"杀掉正在干的活"。

**代价**：故障实例上可能还有少量长请求在跑；需要配合客户端的超时兜底。

---

### A8. 流式响应：读到第一个 chunk 才提交响应头

**背景**：SSE 的标准做法是后端先返回 200 + headers，再逐块推 token。
如果网关收到 headers 就立刻回写给客户端，那么"后端在 prefill 阶段挂掉"时，
客户端已经收到 200，网关无法再重试。

**选择**：`streamCopy` 先 `Read` 第一个 chunk，成功后才 `WriteHeader` + `Flush`。
在第一个字节到达之前，请求仍然是"未提交"状态，可以安全换实例。

**代价**：客户端看到响应头的时间晚了几十毫秒（等于 prefill 时间的一部分），
可忽略；换来了 prefill 失败的可重试性。

**证据**：`TestRetriesWhenStreamDiesBeforeFirstByte`（后端发完 headers 立刻断开，
网关必须换到第二个后端且客户端只看到一份完整输出）。

---

### A9. 首字节之后绝不重试

**选择**：一旦有任何字节写给了客户端，后续错误只记录、不重试。

**为什么**：客户端已经消费了部分 token，换实例重放会得到重复或语义断裂的内容。
这不是"重试会不会成功"的问题，是"重试结果一定错"的问题。

**代价**：decode 中途后端崩溃时，客户端只能拿到截断的流（并感知到连接结束）。
正确做法是客户端带上 `request-id` 做幂等/续写，这超出本项目范围。

**证据**：`TestDoesNotRetryAfterFirstByte`（后端发一个 token 后断开，
第二个后端命中次数必须为 0）。

---

### A10. 超时分为三层：连接 / 首字节 / 总时长

**选择**：
- `DialContext` 5s
- 流式：首字节 30s（`context.WithCancel` + `time.AfterFunc`）
- 非流式：总时长 60s（`context.WithTimeout`）
- `http.Client.Timeout = 0`

**为什么不能设全局 Timeout**：LLM 流式生成 3 分钟很正常。全局 60s 会把所有正常的长请求掐断，
而且表现为"随机失败"，极难排查。

**为什么流式需要首字节超时**：否则后端卡在 prefill 时，客户端会一直等，网关也不会换实例。
首字节到达后不再设总超时——生成多久由模型和 `max_tokens` 决定，网关不该替用户做这个决定。

**代价**：恶意客户端可以通过慢速读取长期占用连接。生产中需要配合
`ReadHeaderTimeout`、连接数上限和反向代理的超时。

---

### A11. 重试前必须缓存 body，并设 8 MiB 上限

**背景**：`r.Body` 是一次性的。转发给后端 A 之后流已读空；A 失败后重试 B，
如果直接用 `r.Body`，发出去的是**空请求**。代码不会报错，日志里看起来"重试成功"。

**选择**：进入代理时 `io.ReadAll(io.LimitReader(r.Body, 8MiB+1))` 缓存，
超过上限直接 413；每次尝试用 `bytes.NewReader(body)` 新建请求。

**代价**：每个请求多一次内存拷贝，最大 8 MiB；LLM 请求体通常只有几 KB。

**证据**：`TestRetrySendsNonEmptyBody` 断言第二个后端收到的 body 与原始 body 逐字节相等。

---

### A12. 非流式响应先整体缓冲，流式不缓冲

**选择**：非流式响应最多缓冲 4 MiB 再写给客户端；超过则退化为边读边写。
流式永远逐块 flush。

**为什么**：非流式请求在"响应体读到一半时后端断开"的情况下，
如果已经写给客户端就无法重试；先缓冲让"截断的 200"也能安全重试。
流式则相反，缓冲会直接毁掉流式体验。

**代价**：非流式响应多一次内存占用（并发 × 响应大小，上限 4 MiB/请求）。

---

### A13. 重试策略：5xx / 连接失败重试，4xx 不重试，排除刚失败的实例

**选择**：最多 2 次；指数退避 + full jitter；`exclude` 集合避免回头打同一个实例；
如果所有健康实例都被排除，回退到完整健康集合（单实例部署时仍然要能重试）。

**为什么 4xx 不重试**：请求本身有问题（模型名错、参数错），换哪个实例都一样，
重试只会放大错误。

**为什么需要 jitter**：故障瞬间大量请求同时重试会形成惊群，把刚恢复的实例再打挂。

**证据**：`TestDoesNotRetry4xx`、`TestFinal5xxIsForwardedNotMasked`。

---

### A14. 限流只做进程级令牌桶（明确不做分布式）

**选择**：`golang.org/x/time/rate`，全局 RPS + burst，默认关闭。

**为什么**：多实例网关的全局限流需要 Redis/中心化配额，复杂度和一致性成本远超本项目收益。
单机令牌桶能保护后端不被打爆，这已经够了。

**代价**：多副本部署时总限额 = 副本数 × RPS。这一点必须在文档里写清楚，不能假装是全局的。

---

### A15. 配置：YAML + 严格字段 + 环境变量覆盖，不做热加载

**选择**：`yaml.Decoder.KnownFields(true)`（拼错字段直接报错，而不是静默忽略）；
`GATEWAY_LISTEN` / `GATEWAY_BACKENDS` 供容器覆盖；改配置需重启。

**为什么不做热加载**：热加载后端列表要处理"旧连接池、在途请求、健康状态迁移"，
是另一个量级的复杂度。重启的代价是几秒的重新探测，对个人项目不值得。

**代价**：扩缩容要重启网关；生产中会用服务发现 + 动态配置，这是明确的未来方向。

## B. 压测与实验

### B1. 闭环保压，而不是 `gather(N)`

**选择**：维持恰好 `concurrency` 个在途请求，完成一个立刻补一个，
测量窗口 = 首个请求开始 → 最后一个请求结束。

**为什么**：`gather(N)` 是"一次性发 N 个"，测的是这批请求的**排干速度**：
没有持续负载、没有排队效应，QPS 会被高估，P99 会被低估。
闭环保压才是客户端连接池的真实行为，也是不同并发档位之间唯一可比的口径。

**代价**：实现比 `gather` 复杂（需要调度循环），且测量时长随并发下降而变长。

---

### B2. 分位数用线性插值

**选择**：`k = (n-1) * p`，在 `floor(k)` 与 `ceil(k)` 之间插值。

**为什么**：常见错误 `sorted(xs)[int(n*0.95)-1]` 在 n=4 时取到索引 2，实际是 P75。
样本量小的时候（每档 100 个请求），这个误差足以让容量基线整体偏移。

**证据**：`test_bench_pro.py::TestPercentile`，其中一条专门断言 P95([1,2,3,4]) = 3.85 而不是 3。

---

### B3. 压测客户端必须绕过系统代理（真实踩坑）

**现象**：本机运行 `pytest` 时，请求 `127.0.0.1:6253` 返回了 Privoxy 的 500 错误页。

**原因**：Windows 注册表里配置了系统代理（`ProxyEnable=1`），
Python 的 HTTP 客户端默认 `trust_env=True`，把 loopback 请求也发给了代理。
在带公司 MITM 代理 / VPN 客户端的机器上，这会静默污染所有延迟数据。

**选择**：`httpx.AsyncClient(trust_env=False)`，并保留 `--use-env-proxy` 显式开启。

**代价**：需要访问外网模型服务时要手动加 flag。

**证据**：`bench_pro.py` 中的注释；`mock_vllm` 联调时复现并修复。

---

### B4. 结果落 JSON，表格由脚本生成

**选择**：每次压测写 `bench/results/<label>-<timestamp>-<rand>.json`，
`bench/summarize.py` 负责生成 Markdown 表格和容量基线。

**为什么**：手抄数字是简历项目最常见的翻车点——改了一个参数，报告里的数字没同步。
JSON 里同时记录环境、配置、每档分位数，任何结论都能回溯到原始数据。

**代价**：多写一个 200 行的脚本；换来的是"报告里的每个数字都能被复现命令生成"。

---

### B5. 不做 TP=1 vs TP=2，不做 SGLang 对比

**理由**（按收益排序）：
- 7B 模型单卡放得下，TP=2 的跨卡 AllReduce 开销大概率大于切分收益，
  结论会是"没有更快"——这个结论对面试的说服力很低，却要花双倍租金。
- SGLang 的 RadixAttention 在 Agent/多轮场景更强，但本项目没有多轮负载，
  强行对比会变成"跑了个分"，讲不出所以然。

**把时间花在哪**：HF Transformers 基线对比（PagedAttention 的收益），
以及容量基线（SRE 视角）。前者有明确倍数结论，后者能回答"需要几张卡"。

**代价**：报告里必须显式写"未做及原因"，不能留空——留空会被当成没想过。

---

### B6. mock server 只用于验证工具链，不产出性能结论

**选择**：`bench/mock_vllm.py` 用标准库实现 OpenAI 兼容接口（含 SSE、usage、prefill/token 延迟），
CI 用它做端到端冒烟。

**为什么**：CI 没有 GPU，但"压测脚本能不能正确解析 SSE / 统计 token / 计算 QPS"必须被测试。
mock 的数字只能证明工具链正确，**不能**写进简历当模型性能。

**证据**：`bench/results/` 里 mock 结果的文件名带 `mock`，`summarize.py` 默认过滤掉，
除非显式 `--include-mock`。

---

## C. 可观测性

### C1. Prometheus 拉模式，而不是应用推

**选择**：网关和 vLLM 都暴露 `/metrics`，Prometheus 每 5s 抓取。

**为什么**：拉模式天然带 `up` 指标（目标是否可达），目标发现和采集解耦；
推模式需要额外处理重试、去重和"实例消失后指标残留"。

**代价**：需要 Prometheus 能网络可达所有实例；容器里靠服务名解析。

---

### C2. 指标命名跟随 vLLM 上游，不做二次封装

**选择**：直接采集 `vllm:*` 原生指标，网关指标用 `gateway_*` 前缀，两者在同一个 dashboard 里关联。

**为什么**：vLLM 的指标名随版本演进（`time_per_output_token_seconds` → `inter_token_latency_seconds`），
二次封装会多一层映射和漂移风险。报告里记录版本映射表，看板按当前版本写。

**代价**：升级 vLLM 大版本时 dashboard 可能要改 PromQL。这一点写进了报告的"版本映射"。

---

### C3. 自定义 Registry，不用全局默认

**选择**：`prometheus.NewRegistry()`，每个 `Metrics` 实例独立。

**为什么**：测试可以并行创建多个实例而不冲突；`/metrics` 输出完全可控，
不会混入 Go runtime 或进程指标（需要时再单独加）。

**代价**：失去了 `promhttp` 默认的 go/process collector；对容量分析影响不大。
